# Touchpad source audit

Audited 2026-11-05 on the running HP EliteBook 840 G10. All times below are Asia/Karachi. This report covers installed sources and offline traces. Independent journal and newer-release investigations are separate.

## Finding

**No symptom-causing code bug is proven. No repair patch is justified yet.**

The two logged incidents are real libinput detections of implausible contact motion **before pointer acceleration and tap processing**. They put the first useful investigation boundary at the coordinates/contact history entering libinput. They do not prove hardware failure, a kernel bug, or a libinput bug. The words `kernel bug` are libinput's log category, chosen by a heuristic.

The 13 retained evdev traces contain no candidate under an offline evaluation of the installed libinput jump predicate. They do not cover either logged incident. They also contain no original HID reports or delivered desktop events. The user's contact-dependent symptoms can therefore remain real even though this corpus does not establish their cause. Experiencing similar trouble on two machines makes common software worth testing, but the second machine's hardware, versions and recordings are missing.

## Device capabilities and expected decoding

[Live stack snapshot](/home/elhaam/.cache/touchpad-investigation/source-audit/audit-20261105T164152/live-stack.txt), [saved 675-byte descriptor](/home/elhaam/.cache/touchpad-investigation/source-audit/audit-20261105T164152/report_descriptor.bin), and [offline descriptor fields](/home/elhaam/.cache/touchpad-investigation/source-audit/audit-20261105T164152/descriptor-fields.json) establish the following. The descriptor is from the HID identity created by the intentional 16:30:38 rebind, not a raw report recording of a failure.

- Live drivers are `i2c_hid_acpi` and `hid-multitouch`, HID identity `0018:04F3:31EC.0016`, group `0004`, Windows Precision Touchpad. This is the generic HID multitouch path, not the proprietary `elan_i2c`, PS/2 elantech, or USB `hid-elan` report decoder.
- Input report ID `0x54` is 29 bytes including report ID, or 31 bytes with the I2C HID length prefix. It contains a physical button bit, a four-bit contact count, a 16-bit scan time, and five five-byte contact records. Each record contains Confidence, Tip Switch, four-bit Contact ID and unsigned little-endian 16-bit X/Y. Unused bits are padding.
- X is `0..3689`, physical `117.00 mm`; Y is `0..2410`, physical `77.00 mm`. HID units are centimetres with exponent -3. [hidinput_calc_abs_res](/home/elhaam/.cache/touchpad-investigation/source-audit/audit-20261105T164152/linux-pop-b24b425/drivers/hid/hid-input.c:245) rounds this to X resolution 32 units/mm and Y 31 units/mm, exactly as every saved trace reports. Libinput derives about `115.28 × 77.74 mm` from these rounded resolutions. This small static rounding is not evidence of an intermittent decoding error.
- There are no pressure, width, height or In Range input fields in this touchpad report. Confidence supplies firmware palm classification. The descriptor also has a legacy relative mouse report `0x01` and vendor report `0x5c`. Feature-report declarations are not their current values; this audit did not issue feature writes or query firmware through HID commands.

The raw-report layout is directly compatible with the generic driver. A raw `0x54` payload, excluding its ID byte, has button/contact count in byte 0, scan time in bytes 1-2, then record `i` at byte `3 + 5*i`. That record has Confidence in bit 0, Tip in bit 1, Contact ID in bits 4-7, X in its next two bytes and Y in its final two bytes. This makes an offline raw/evdev comparison possible once failure reports exist. Firmware version `0x0008` is the version supplied for this investigation; the firmware implementation itself was not available for inspection.

### Kernel contact lifecycle and quirks

The [generic Windows class](/home/elhaam/.cache/touchpad-investigation/source-audit/audit-20261105T164152/linux-pop-b24b425/drivers/hid/hid-multitouch.c:283) selects valid-record handling, duplicate suppression, accurate contact count, hover support, a sticky-contact timeout and PTP button handling. The live sysfs class quirks value `334864`, hexadecimal `0x51c10`, matches those flags. [mt_show_quirks](/home/elhaam/.cache/touchpad-investigation/source-audit/audit-20261105T164152/linux-pop-b24b425/drivers/hid/hid-multitouch.c:427) exposes class defaults; application-specific flags can differ. In particular [Confidence mapping](/home/elhaam/.cache/touchpad-investigation/source-audit/audit-20261105T164152/linux-pop-b24b425/drivers/hid/hid-multitouch.c:823) adds palm support for this touchpad application. No `31EC`-specific slot quirk appears in the device table. See the [generic table entry](/home/elhaam/.cache/touchpad-investigation/source-audit/audit-20261105T164152/linux-pop-b24b425/drivers/hid/hid-multitouch.c:2407) and [authoritative pinned driver](https://github.com/pop-os/linux/blob/b24b425c7e28f365efeacbaf093ed6a07da8b934/drivers/hid/hid-multitouch.c).

[I2C i2c_hid_get_input](/home/elhaam/.cache/touchpad-investigation/source-audit/audit-20261105T164152/linux-pop-b24b425/drivers/hid/i2c-hid/i2c-hid-core.c:523) reads the descriptor's maximum input length, rejects a short transaction, treats a zero length as reset completion, checks the little-endian report length, and passes the payload to HID core. Its [ELAN vendor quirks](/home/elhaam/.cache/touchpad-investigation/source-audit/audit-20261105T164152/linux-pop-b24b425/drivers/hid/i2c-hid/i2c-hid-core.c:145) avoid wakeup after reset and ignore bogus `0xffff` IRQ responses. They do not smooth or correct coordinates.

[hid_report_raw_event](/home/elhaam/.cache/touchpad-investigation/source-audit/audit-20261105T164152/linux-pop-b24b425/drivers/hid/hid-core.c:2020) identifies the report and [hid_input_fetch_field](/home/elhaam/.cache/touchpad-investigation/source-audit/audit-20261105T164152/linux-pop-b24b425/drivers/hid/hid-core.c:1581) extracts descriptor-defined bit fields. Importantly, HID core zero-pads a report that is shorter than its declared report size. Thus an I2C response with a structurally accepted length but truncated HID payload could produce zero-valued fields. That is an existing recovery behavior, not a demonstrated defect in this case. There are no failure report lengths to test this hypothesis.

[mt_store_field](/home/elhaam/.cache/touchpad-investigation/source-audit/audit-20261105T164152/linux-pop-b24b425/drivers/hid/hid-multitouch.c:699) saves pointers to decoded values, allocating the next contact record when a usage repeats after Contact ID/X/Y are complete. [mt_touch_report](/home/elhaam/.cache/touchpad-investigation/source-audit/audit-20261105T164152/linux-pop-b24b425/drivers/hid/hid-multitouch.c:1236) uses Contact Count and Scan Time to assemble frames, processes records, then synchronizes once the expected contact count is reached. It supports continuation reports with zero Contact Count.

[mt_compute_slot](/home/elhaam/.cache/touchpad-investigation/source-audit/audit-20261105T164152/linux-pop-b24b425/drivers/hid/hid-multitouch.c:953) calls [input_mt_get_slot_by_key](/home/elhaam/.cache/touchpad-investigation/source-audit/audit-20261105T164152/linux-pop-b24b425/drivers/input/input-mt.c:508) for this class. Active firmware Contact IDs keep their existing kernel slots. New IDs use an inactive slot not already used in the current frame. **Nearest-coordinate slot matching is not used here.** The kernel's `input_mt_assign_slots` distance-matching algorithm is therefore not a candidate on this path. Libmtdev's Type A conversion is also bypassed for this Type B device with `ABS_MT_SLOT`.

[mt_process_slot](/home/elhaam/.cache/touchpad-investigation/source-audit/audit-20261105T164152/linux-pop-b24b425/drivers/hid/hid-multitouch.c:1047) checks count/duplicates, derives active state from Tip or In Range, sets palm tool type when Confidence is false, and reports X/Y for active contacts. This descriptor has no In Range field, so active state follows Tip Switch. [input_mt_report_slot_state](/home/elhaam/.cache/touchpad-investigation/source-audit/audit-20261105T164152/linux-pop-b24b425/drivers/input/input-mt.c:137) assigns a kernel tracking ID on activation and sends `-1` on release. Kernel tracking IDs are not the firmware's four-bit Contact IDs. [input_mt_sync_frame](/home/elhaam/.cache/touchpad-investigation/source-audit/audit-20261105T164152/linux-pop-b24b425/drivers/input/input-mt.c:326) updates pointer/finger-count emulation and frame state. [input_handle_abs_event](/home/elhaam/.cache/touchpad-investigation/source-audit/audit-20261105T164152/linux-pop-b24b425/drivers/input/input.c:155) suppresses unchanged fields, so absent X or Y evdev events mean retain the previous value.

This class expects firmware to report releases. It does not use `NOT_SEEN_MEANS_UP` to release every omitted contact. Its [100 ms sticky-contact timeout](/home/elhaam/.cache/touchpad-investigation/source-audit/audit-20261105T164152/linux-pop-b24b425/drivers/hid/hid-multitouch.c:1307) and [timeout handler](/home/elhaam/.cache/touchpad-investigation/source-audit/audit-20261105T164152/linux-pop-b24b425/drivers/hid/hid-multitouch.c:1798) handle a stalled report stream. A lost release, reused live Contact ID, duplicate ID, incorrect count or truncated report is therefore a concrete hypothesis. Only raw HID aligned with evdev can distinguish these from a kernel implementation error.

## Meaning of the libinput diagnostic

The exact [installed tp_detect_jumps](/home/elhaam/.cache/touchpad-investigation/source-audit/audit-20261105T164152/libinput-1.20.0/src/evdev-mt-touchpad.c:1487) computes physical displacement from the current contact position and previous history sample. For positive intervals up to 30 ms it normalizes distance to a 12 ms interval:

```
normalized_distance = hypot(dx / x_resolution, dy / y_resolution) * 12000 / dt_us
jump = normalized_distance > 20 || normalized_distance - previous_normalized_distance > 7
```

It skips zero/long intervals and some model quirks. On a typical 8 ms report, those limits correspond to over 13.33 mm of travel or over 4.67 mm of increased travel versus the preceding normalized delta. No matching libinput model quirk was printed by `libinput quirks list /dev/input/event5`; the installed Elantech/HP name matches do not select this device.

[tp_process_state](/home/elhaam/.cache/touchpad-investigation/source-audit/audit-20261105T164152/libinput-1.20.0/src/evdev-mt-touchpad.c:1710) calls this predicate before palm/wobble/hysteresis processing. On a hit it logs `Touch jump detected and discarded` and clears that contact's motion history. The new point becomes a fresh baseline, so the anomalous delta is withheld from normal pointer motion. This does not guarantee all surrounding movement or generated actions are correct. Changes in contact count also reset history, including the following frame. Warnings are rate-limited to five per 24 hours per initialized device/context, [at initialization](/home/elhaam/.cache/touchpad-investigation/source-audit/audit-20261105T164152/libinput-1.20.0/src/evdev-mt-touchpad.c:3664). Warning counts are not fault counts.

The custom recorder's [40 mm/20 ms detector](/home/elhaam/dotfiles/scripts/touchpad-watch.py:159) has a different distance/speed test, startup suppression, repeated-jump requirement and cooldowns. It cannot validate libinput's acceptance of a stream.

There is also a separate [MSC_TIMESTAMP wakeup-history correction](/home/elhaam/.cache/touchpad-investigation/source-audit/audit-20261105T164152/libinput-1.20.0/src/evdev-mt-touchpad.c:1605). After a zero device timestamp, it checks the next intervals and can rewrite history to account for buffered or swallowed frames. [tp_pre_process_state](/home/elhaam/.cache/touchpad-investigation/source-audit/audit-20261105T164152/libinput-1.20.0/src/evdev-mt-touchpad.c:1687) runs it before the general jump predicate. The kernel [mt_compute_timestamp](/home/elhaam/.cache/touchpad-investigation/source-audit/audit-20261105T164152/linux-pop-b24b425/drivers/hid/hid-multitouch.c:1018) derives MSC timestamps from the HID scan counter. Failure capture should preserve both kernel event times and scan/MSC times. The offline predicate helper does not reproduce this history correction.

The [saved journal excerpt](/home/elhaam/.cache/touchpad-investigation/source-audit/audit-20261105T164152/jump-journal.txt) confirms both Touchégg and Xorg emitted the diagnostic on Nov 3 at 16:05:34.174/175 and Nov 5 at 13:39:44.966/967. Xorg's [log handler](/home/elhaam/.cache/touchpad-investigation/source-audit/audit-20261105T164152/xserver-xorg-input-libinput-1.2.1/src/xf86libinput.c:2643) forwards libinput errors. Touchégg creates its [separate context and seat reader](/home/elhaam/.cache/touchpad-investigation/source-audit/audit-20261105T164152/touchegg-2.0.15pop0~1674691430~22.04~2e20838/src/gesture-gatherer/libinput-gesture-gatherer.cpp:53). These are two consumers detecting the same underlying motion, not independent reports of two hardware faults. An Xorg-only postprocessing bug does not explain the daemon's matching pre-acceleration warning; a common libinput history bug or false-positive heuristic remains possible.

## Acceleration, tapping and gestures

[evdev_device_dispatch](/home/elhaam/.cache/touchpad-investigation/source-audit/audit-20261105T164152/libinput-1.20.0/src/evdev.c:1127) obtains evdev events through libevdev, handles `SYN_DROPPED` by resynchronizing state, and passes timestamped events through [evdev_process_event](/home/elhaam/.cache/touchpad-investigation/source-audit/audit-20261105T164152/libinput-1.20.0/src/evdev.c:1049). [tp_process_absolute](/home/elhaam/.cache/touchpad-investigation/source-audit/audit-20261105T164152/libinput-1.20.0/src/evdev-mt-touchpad.c:500) selects the reported slot and updates coordinates/tracking lifecycle. [tp_new_touch](/home/elhaam/.cache/touchpad-investigation/source-audit/audit-20261105T164152/libinput-1.20.0/src/evdev-mt-touchpad.c:314) resets contact history. Libinput does not geometrically reassign these hardware-tracked slots.

After contact processing, [tp_post_events](/home/elhaam/.cache/touchpad-investigation/source-audit/audit-20261105T164152/libinput-1.20.0/src/evdev-mt-touchpad.c:1856) runs tapping/buttons, suppression during typing, scrolling and gestures. [tp_gesture_post_pointer_motion](/home/elhaam/.cache/touchpad-investigation/source-audit/audit-20261105T164152/libinput-1.20.0/src/evdev-mt-touchpad-gestures.c:224) obtains motion and passes it through [tp_filter_motion](/home/elhaam/.cache/touchpad-investigation/source-audit/audit-20261105T164152/libinput-1.20.0/src/evdev-mt-touchpad.c:61). [The adaptive filter](/home/elhaam/.cache/touchpad-investigation/source-audit/audit-20261105T164152/libinput-1.20.0/src/filter-touchpad.c:229) calculates a velocity-dependent scalar and applies it to the raw delta. Xorg [xf86libinput_handle_motion](/home/elhaam/.cache/touchpad-investigation/source-audit/audit-20261105T164152/xserver-xorg-input-libinput-1.2.1/src/xf86libinput.c:1463) forwards accelerated and unaccelerated values to the server. The driver explicitly [disables the server's additional acceleration](/home/elhaam/.cache/touchpad-investigation/source-audit/audit-20261105T164152/xserver-xorg-input-libinput-1.2.1/src/xf86libinput.c:3725).

The restored speed `0.73529411764705888` produces speed factor about `3.58136` versus `1.00088` at speed zero in [speed_factor](/home/elhaam/.cache/touchpad-investigation/source-audit/audit-20261105T164152/libinput-1.20.0/src/filter-touchpad.c:160). That is about 3.58 times the same adaptive curve at zero speed, not a universal pixels/mm factor. It can amplify small coordinate errors that pass jump detection. It cannot create the upstream diagnostic, change firmware IDs or explain an input coordinate discontinuity by itself. The user's report that the speed/tap-drag trial worsened behavior means that trial is not a repair; the baseline remains restored.

Tapping uses a [180 ms timeout and 1.3 mm movement threshold](/home/elhaam/.cache/touchpad-investigation/source-audit/audit-20261105T164152/libinput-1.20.0/src/evdev-mt-touchpad-tap.c:32). [tp_tap_touch_handle_event](/home/elhaam/.cache/touchpad-investigation/source-audit/audit-20261105T164152/libinput-1.20.0/src/evdev-mt-touchpad-tap.c:222) can emit a button press on release without any kernel `BTN_LEFT`. With tap-drag enabled, a following contact can continue a drag through [tp_tap_tapped_handle_event](/home/elhaam/.cache/touchpad-investigation/source-audit/audit-20261105T164152/libinput-1.20.0/src/evdev-mt-touchpad-tap.c:315). Faulty release/recontact transitions could therefore generate clicks/dragging with individually plausible positions. Short contacts can also be intentional taps; the recordings do not distinguish intention.

Touchégg's [event switch](/home/elhaam/.cache/touchpad-investigation/source-audit/audit-20261105T164152/touchegg-2.0.15pop0~1674691430~22.04~2e20838/src/gesture-gatherer/libinput-gesture-gatherer.cpp:101) handles swipe/pinch and touchscreen touch events, not ordinary pointer motion. Configured actions can synthesize X events, including [button clicks](/home/elhaam/.cache/touchpad-investigation/source-audit/audit-20261105T164152/touchegg-2.0.15pop0~1674691430~22.04~2e20838/src/window-system/x11.cpp:466). This remains a possible explanation for unintended actions during gestures. It does not explain the pre-gesture coordinate warning. This audit does not establish that any configured action fired during a symptom.

It does not implement libinput's full lifecycle, two-frame motion resets, hover, palm classification, hysteresis, MSC history correction, taps, timers or emitted pointer motion. Its candidate counts are not a claim about exact libinput dispatch output.

Across 13 files, including overlapping and duplicate windows, there are 58,475 recorded events, 11,056 touchpad frames and 11,618 same-tracking-ID comparisons within 30 ms. These totals are not independent samples. Findings:

- Zero C jump-predicate candidates in this adjacent-frame model, and zero custom 40 mm predicate matches.
- No `SYN_DROPPED`, truncation flags, X/Y values outside declared ranges, or positive tracking-ID replacement without an intervening `-1` in the captured event streams.

## Falsifiable next experiment and fix boundary

For the next labeled failure, retain simultaneous bounded recordings of raw touchpad HID input, both existing evdev nodes, and outgoing X11 pointer/button events, all aligned to monotonic time. The existing recorder can mark evdev without resetting. Raw HID capture would need a separate read-only observer with permission to read this device; no HID mode/feature writes, grabs, accessibility services or virtual devices are needed. Opening hidraw for reading and observing descriptor-defined reports is enough to compare the host-received HID payload with evdev. This experiment is proposed, not started here.

A diagnostic build of libinput can also add logging immediately around `tp_detect_jumps`: slot, current/previous coordinates, timestamps, history count, previous normalized delta, contact-count resets and the predicate result. That is instrumentation to find the cause, not a repair. Pair this with source-qualified X11 button events and libinput tap/gesture state. Preserve the restored baseline during capture; mark the symptom before any intentional rebind.

1. If a stable raw firmware Contact ID itself jumps in X/Y and evdev faithfully follows it, investigate the controller/firmware/sensor or transport payload. A narrow kernel quirk might suppress a documented bad-report pattern, but it would be a workaround until the producer is understood. Raw HID captures show bytes received by the host; separating firmware output from corruption on the electrical bus needs lower-level evidence.
2. If raw coordinates, IDs and contact count stay correct but evdev swaps slot occupants, misses a release or changes coordinates, the fix belongs in HID decoding/frame assembly/slot handling. Recreate the failing sequence offline and patch the exact violated invariant in hid-multitouch or input-mt. Do not apply nearest-neighbor fixes to an ID-keyed path without evidence.
3. If raw and evdev trajectories/lifecycles are correct but libinput history combines contacts or emits an unexpected delta/button, the fix belongs in libinput's lifecycle/history, tap or gesture logic. Reproduce with the same event sequence and baseline configuration before changing its filter.
4. If libinput output is correct but the visible action differs, investigate the Xorg/GNOME/application or Touchégg action boundary. Compare X11 event source IDs and the action configuration. Pure acceleration sensitivity predicts a different scalar output for the same valid input; it predicts no raw-ID/slot corruption and no change to the pre-acceleration jump predicate.

The first branch to instrument is the raw-HID/evdev boundary because two independent libinput contexts reported the coordinate warning. Smaller motion errors and unintended actions still require the later boundaries. A future fork/build/install should target whichever boundary fails this comparison. There is no evidence-based repair patch to propose today.

- Linux HID/I2C/input stack, including the Pop distribution source. [Linux COPYING](https://github.com/pop-os/linux/blob/b24b425c7e28f365efeacbaf093ed6a07da8b934/COPYING) specifies GPL-2.0-only with the syscall exception. Individual file notices govern those files; hid-multitouch is GPL-2.0-or-later, input-mt is GPL-2.0-only, and I2C HID core has a GPL notice referring to the top-level COPYING. [Local source license](/home/elhaam/.cache/touchpad-investigation/source-audit/audit-20261105T164152/linux-pop-b24b425/COPYING:1).
- Libinput. [MIT license](https://gitlab.freedesktop.org/libinput/libinput/-/blob/1.20.0/COPYING), [local COPYING](/home/elhaam/.cache/touchpad-investigation/source-audit/audit-20261105T164152/libinput-1.20.0/COPYING:1).
- X.Org xf86-input-libinput. [Upstream project](https://gitlab.freedesktop.org/xorg/driver/xf86-input-libinput), [MIT COPYING](/home/elhaam/.cache/touchpad-investigation/source-audit/audit-20261105T164152/xserver-xorg-input-libinput-1.2.1/COPYING:1).
- Touchégg. [Upstream project](https://github.com/JoseExposito/touchegg), GPL-3.0-or-later, [exact distro copyright](/home/elhaam/.cache/touchpad-investigation/source-audit/audit-20261105T164152/touchegg-2.0.15pop0~1674691430~22.04~2e20838/debian/copyright:1).
- Libevdev `1.12.1+dfsg-1` is the installed event-reader dependency, [MIT upstream project](https://gitlab.freedesktop.org/libevdev/libevdev). Libmtdev `1.1.6-1build4` is installed, [MIT upstream project](https://bitmath.org/code/mtdev/), but Type A conversion is not used for this device's Type B slots. Their implementations were not independently audited here; libinput's reader/resync and conversion-selection call sites were.
