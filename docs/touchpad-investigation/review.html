Other anomalies and what they mean
  • Two incomplete reports. On Oct 11 and Oct 15, the kernel received a 31-byte report declaring a length of 65,280 bytes. The driver rejected it. Both occurred around resume; neither was within 60 seconds of a logged jump.
  • 58 scheduling warnings. Several input consumers processed events late. Fifteen messages named the touchpad. These are timing faults, distinct from coordinate-jump detections.
  • Four disconnect episodes. All match manual driver resets. They are not evidence of spontaneous device disconnection.
  • Desktop and kernel stalls. Graphics assertions, garbage-collection stalls, hung tasks and audio faults also appear. The audit did not establish them as the cause of wrong touchpad coordinates.
  • Substantial log suppression. Counts are lower bounds on emitted diagnostics. Missing messages and overwritten history cannot be reconstructed.

Where a source fix could belong

The Linux drivers, libinput and the Xorg bridge are open source. The touchpad firmware's source availability has not been established. This machine uses the generic Windows Precision Touchpad path, not the separate elan_i2c driver. Exact source provenance.

  1. 1. DeviceFirmware emits contact IDs, coordinates and touch state as HID reports.
  2. 2. KernelI2C-HID and hid-multitouch decode reports into evdev contacts and slots.
  3. 3. LibinputChecks contact motion, then applies tapping, gestures and acceleration.
  4. 4. DesktopXorg, GNOME and apps receive pointer movement and button events.

The jump warning originates in stage 3, before acceleration and tapping. That narrows this warning to incoming coordinates or libinput's interpretation of contact history. Other interaction errors may originate later.

Use the first incorrect event to choose the patch

Coordinates are already wrong in the HID bytes

Required evidence: a stationary fingertip or known stroke, a stable firmware contact ID, and a coordinate discontinuity already present in the raw report.

Direction: investigate firmware, sensor conditions and transport. Seek an exact HP/ELAN firmware fix. A device-specific kernel filter is only justified by a repeatable bad-report pattern and tests that preserve real fast motion.

This locates the problem before libinput. It still does not prove broken physical hardware or distinguish controller output from electrical corruption.

HID is correct, but evdev contacts are wrong

Required evidence: aligned HID reports show correct IDs, releases and coordinates while the kernel produces a wrong slot, missed release or changed position.

Direction: reproduce that report sequence and fix the first broken rule in hid-multitouch.c frame/contact handling or input-mt.c. Verify that each firmware contact remains associated with the correct kernel slot.

This device uses ID-based slots. A nearest-coordinate matching patch would target a path it does not use.

Kernel contacts are correct, but pointer output is wrong

Required evidence: the same event sequence produces an incorrect delta, click or drag in the installed library. Compare it against 1.32.0 using matching options in an isolated test.

Direction: inspect tp_new_touch, tp_end_touch, motion-history resets and tap state. If the newer version fixes the sequence, identify the fixing commit and backport it. Otherwise create a regression test and correct the first broken lifecycle rule.

Do not disable jump protection or blindly discard the first movement of every touch. Either can mask the fault or damage normal input.

Processed input is correct, but the desktop acts incorrectly

Required evidence: correct contact and processed motion alongside an unexpected desktop button, pointer source or application action.

Direction: inspect XInput source IDs, Touchégg actions and application handling. Use a controlled gesture-service or clean-session comparison only after the event capture points here.

A tap can generate a button event without a physical button press in evdev. That is normal behavior unless the contact sequence or resulting action is wrong.

Suggested directions, in order

  1. Capture a labeled failure at all three boundaries

    First choice · 90 seconds of observation · Administrator read access needed

    Record raw HID and kernel events with the standard libinput-record --with-hidraw tool while capturing X11 pointer/button events. Perform a stationary hold, a slow stroke and the action that fails. Label the exact failure and time before any reset.

    Success condition: one captured occurrence with a known hand action and aligned events. The helper is prepared and its device checks passed. The privileged capture has not run; the private credential request expired.

  2. Compare current and newer libinput without replacing the desktop library

    Next if contacts are valid · Isolated 1.32.0 tools already built

    Match speed, tap, drag and acceleration settings in both diagnostic contexts. Compare their output for the same failing input. Replaying into the live desktop is not the proposed test; use an isolated input environment.

    Success condition: old software fails and new software passes the same sequence. Then bisect to a specific commit. A successful build or newer version number is not sufficient.

  3. Build a minimal fix in the layer that fails

    Conditional repair · Preserve distro security patches and a rollback package

    Use the captured sequence as a regression fixture. Apply the smallest correction to contact lifecycle, report handling or history. Build packages for this OS instead of overwriting system libraries. Test release/recontact, multiple fingers, palms and normal movement as well as the failing sequence.

    Success condition: a failing test before the patch, a passing test afterward, and normal live behavior after a controlled installation. Library replacement requires a session restart to affect existing consumers; a kernel change requires rebooting.

  4. Test a shared model or firmware cause under controlled conditions

    Useful parallel evidence · More disruptive tests need a planned time

    Verify IDs and firmware on both laptops. Compare the same short action on battery and AC, with a clean dry pad and no dock. Then compare an already installed alternate OS or a live environment on the same laptop, keeping track of which kernel and userspace changed.

    Success condition: repeatable outcomes tied to one changed condition. Similar symptoms across identical machines are evidence of a common cause, not proof that hardware is impossible.

Directions to avoid for now

Another sensitivity guess, automatic reset loops, disabling jump detection, unrelated ELAN quirks, a whole-system upgrade, or a speculative firmware flash. None has a demonstrated match to the captured evidence.

What would count as a permanent repair?

  • The actual failure is captured and reproducible.
  • A source change explains why that sequence failed.
  • The same sequence fails before the change and passes afterward.
  • Normal movement, clicks, dragging and multiple contacts still work.
  • The fix runs in the real desktop and remains effective through relevant resume and recontact conditions.
  • Installation is packaged, its restart needs are understood, and rollback is available.

No finite test can promise the problem will never recur. This standard gives us a repair tied to evidence rather than another temporary adjustment.

What would justify a hardware diagnosis?

A kernel log saying kernel bug does not prove a hardware defect. Bad HID coordinates can come from firmware, sensing or transport; host captures alone do not distinguish all three.

A stronger case needs repeatable bad device-level reports under controlled physical conditions, comparisons across independent software stacks on the same unit, and, where appropriate, vendor diagnostics or component-level testing. We do not currently have that proof.
